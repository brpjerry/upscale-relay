This release lets relay playback ride out network dropouts, buffers minutes
of video instead of 10 seconds, and runs the server on Linux. Upscale Relay
Android v0.24.0 works with this server unchanged.

Playback through network dropouts:

- A session now survives a lost connection to the server. Until now, a
  dropout longer than about 10-30 s ended playback with "The connection to
  the server was lost", however much video was buffered. The desktop client
  now keeps playing from its buffer and reconnects in the background (the
  status bar says so). Once the network is back, it carries on with the same
  session. The server holds a session for two minutes from when it notices
  the loss, which takes up to 30 s. Playback goes on if the client
  reconnects within that hold and the video connections survived the
  dropout, which they usually do. Otherwise it ends as before. The player
  waits on "Buffering…" if its buffer runs out first. In a test through a
  proxy that held all traffic for 45 s, playback went on without a dropped
  frame, and the session carried on 2 s after traffic flowed again; the same
  dropout used to end playback 16.5 s in. Older servers end the session as
  before.
- The relay buffer is sized by the player's cache instead of being fixed at
  10 s. "Cache size" (Streaming settings, 256 MB to 5 GB, default 768 MB)
  sets the player's cache. The client asks the server to keep as much video
  buffered as fits in it at the bitrate it receives, which is minutes at
  typical HEVC qualities. The server therefore works further ahead, and a
  seek discards more of that work. `relay-client --buffer-s S` asks for a
  fixed buffer.

Server:

- The server runs on Linux and is packaged for Arch Linux
  (`upscale-relay-server`, with a systemd user unit;
  `systemctl --user start upscale-relay-server`). CUDA, cuDNN and FFmpeg
  come from pacman. ONNX Runtime and TensorRT are downloaded once per user
  by `relay-server --install-nvidia-runtime` (about 4 GB, 2.8 GB on disk),
  because Arch's builds cannot run TensorRT models. Passthrough works
  without them. The tray GUI works on Linux desktops with a StatusNotifierItem
  tray. `docs/SERVER_LINUX.md` has the setup.
- The TensorRT engine cache moved beside the models
  (`<models-dir>/.trt_cache`), on Windows too. Where the models folder is not
  `./models`, each model's engine is rebuilt once: let that happen while the
  GPU is idle, since an engine built on a busy GPU stays slow.
- A session held for a reconnect keeps its GPU memory and video encoder for
  up to two minutes. It starts no new work meanwhile; frames already in
  flight finish. `GET /status` lists it with
  `control_attached: false`.
- Fixed: an inference worker that crashed between frames made the session's
  teardown fail, and the server then asked to be restarted.

Desktop client:

- On Linux (Wayland) with fractional scaling, sessions are sized for the
  screen's real pixels. A 4K screen at 150% asked the server for 5120x2880
  and now asks for 3840x2160. Rotated screens report their rotated size.

The Arch Linux packages (now `upscale-relay-common`, `-client` and
`-server`) and the Windows server ZIPs use version 0.26.0. Upgrading the
0.25.0 client package moves the shared modules into `upscale-relay-common`
in one `pacman -U`. No protocol version change is required. Everything new
on the wire is optional: `buffer_target_ms` (PROTOCOL §5) and session resume
(`session_resume`, `open_session.resume`, `resume_session`; §1.2). Older
clients, Android v0.24.0 among them, keep a 10 s buffer, and their sessions
end with the connection as before.
