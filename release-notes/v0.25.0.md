This release keeps HDR video HDR from the source to the screen, applies
Dolby Vision and HDR10+ on the server for SDR screens, and fixes upscaled
video that came out slightly darker than its source. Upscale Relay Android
v0.24.0 works with this server unchanged.

Fixed:

- Upscaled video matches the source's brightness again. Every model session
  on an 8-bit stream, the default, came out darker than the original. The
  server's conversion to RGB, before the model, read 8-bit sources 1-1.5
  levels (out of 255) dark. It read 10-bit sources about 2 levels dark, so
  their white reached only 253. Colour edges were also slightly blockier
  than the source. `upscale-cli run` with a model was affected the same
  way. Passthrough was affected only in cover mode. The bug dates from the
  first release. On lossless model sessions, the mean brightness was 1.1-1.7
  levels below the source before the fix and is within 0.6 levels after it.
  The accurate conversion costs the server about 2 ms more per 1080p frame.

HDR:

- HDR video stays 10-bit with its metadata. HDR sources (PQ and HLG) stream
  at 10 bits to clients that ask for it, and the desktop client always
  does. The stream keeps the source's mastering display, light level and
  HDR10+ metadata, and the Dolby Vision metadata of profile 8. Until now every
  stream was 8-bit with the HDR metadata dropped, with a model or in
  passthrough. Where mpv still tone-maps HDR to SDR (on Windows and on SDR
  screens), it now works from the real 10-bit signal.
- On Linux the desktop client shows HDR video as HDR ("Show HDR videos in
  HDR", on by default). A PQ or HLG video on a screen in HDR mode plays on
  an HDR surface at the display's peak brightness, and the interface draws
  over it as before. It needs Qt 6.10.2 or newer and a Wayland compositor
  with the colour management protocol, and was verified on Hyprland 0.56.
  On Hyprland, fullscreen on an SDR screen switches the screen to HDR for
  the video (`render:cm_auto_hdr`) and back when fullscreen ends. On
  Windows it is an opt-in prototype (`RELAY_HDR_WINDOWS=1`).
- The server applies Dolby Vision and HDR10+ for the client's screen. mpv's
  renderer in the desktop client uses only static HDR metadata. For an SDR
  screen, a server with a suitable FFmpeg (see Server below) now tone-maps
  Dolby Vision (profiles 5, 7, 8.1 and 8.4) and HDR10+ by their dynamic
  metadata. For an HDR screen, it applies the reshaping of Dolby Vision
  profile 5, whose colours were wrong before. The stream switches when the
  screen does, for example when Hyprland switches it to HDR in fullscreen,
  and the info card names what the server applied.
- "Use 10 bit video" (off by default) streams every video at 10 bits, 8-bit
  sources included. With it off, only HDR sources stream at 10 bits. At
  `hevc-qp4` it made streams 20-46% smaller in our tests. With a model it
  costs the server a good deal: on an RTX 5090 a 1080p source went from 51
  to 31.5 fps, enough for 24 fps video but marginal for 30.

Desktop client:

- "Use passthrough for 4K or higher resolution videos" (off by default)
  plays 4K and larger sources without the model. A 2x model on a 4K source
  runs well below realtime, and its 8K output was then scaled down to the
  display anyway.
- On Linux with an Intel GPU, video decodes zero-copy instead of copying
  each frame back from the GPU. A 2880x1620 10-bit clip loads in 480 ms
  instead of 1,021 ms (median). Fullscreen playback on battery draws
  0.9-1.2 W less, and the player's CPU use falls from 44-54% to 17-18%.
  Other GPUs keep copy-back, and `RELAY_HWDEC` overrides the mode.
- On Linux the screen stays awake during playback for idle handlers, such as
  some dimmers, that watch only logind: the client now also takes a logind
  idle lock while it plays.

Server:

- Display mapping needs an FFmpeg build with libplacebo on Vulkan, and the
  gyan.dev full build has one (`winget install Gyan.FFmpeg`). The server
  looks for it in `--ffmpeg PATH`, then `$RELAY_FFMPEG`, then `ffmpeg` on
  PATH, and the tray GUI uses the last two. The server tries it at start-up
  and maps only if it works. Without it everything else works as before.
  `--no-display-mapping` turns mapping off.
- 10-bit sessions with a model run it on 16-bit RGB, so TensorRT builds a
  second engine for each model the first time such a session starts. As
  with any engine, build it while the GPU is idle.
- PyAV 19 or newer is required.

The Arch Linux client package and Windows server ZIPs use version 0.25.0.
No protocol version change is required. Everything new on the wire is
optional: `high_bit_depth`, `display_target` and the fields that answer
them. Older clients keep their 8-bit SDR streams, and the desktop client
asks only for what a server advertises.
